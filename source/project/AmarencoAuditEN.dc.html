Project 02 March – June 2025 Amarenco, Toulouse Data quality · SynaptiQ API

PVsyst ↔ SynaptiQ quality control

The context

The monitoring platform reported performance ratios nobody could explain: a plant's digital twin and its PVsyst study did not tell the same story.

What I built

Two automated extractions, PVsyst studies from SharePoint and the digital twin from the SynaptiQ API, then a comparator that pinpoints the faulty PVsyst studies or configurations.

Company
Amarenco, solar power producer
Role
Consulting engineer in PV operations and author of the tools
Period
March – June 2025, within the Amarenco assignment
Scope
970 active plants monitored in SynaptiQ, about 7,500 PVsyst files
Deliverables
Python scripts, digital-twin export, Excel discrepancy report

The story

A performance ratio nobody could explain

Three sources that did not talk to each other

  • SharePoint

    Each project's PVsyst studies, filed across several folder structures, often in several versions.

  • Internal technical database

    An Excel workbook filled in and updated by hand: nothing flowed into it automatically from SharePoint.

  • SynaptiQ

    Each plant's digital twin, from which the monitoring platform computes expected production and the PR.

  1. 01

    The problem

    Finding a design value meant searching SharePoint by hand, project by project, then copying it into the database. It was slow, and the database was never up to date.

  2. 02

    First answer

    Retrieve every PVsyst study from SharePoint automatically and extract its data, with no manual entry.

  3. 03

    The discovery

    Analyzing production, some PR values stayed unexplainable: the gap between theory and reality came not from the plants but from the models themselves. The SynaptiQ configuration did not always match the PVsyst study, and neither fed the database.

  4. 04

    The decision

    Extract the entire SynaptiQ API and check it against the PVsyst studies, to pinpoint the culprit in each case: a misconfigured digital twin, a wrong PVsyst simulation, or both.

The goal

Make the PR explainable again and recover performance on every SPV: expected production computed from a configuration that matches what was actually built.

The method

Did PVsyst and the monitoring platform describe the same plant?

Every plant has two references: the PVsyst study, which describes what was designed, and the SynaptiQ configuration, from which the monitoring platform computes expected production and the performance ratio. A wrong orientation or module count skews the indicators reported to shareholders. I automated the cross-check across the whole fleet.

The pipeline, script by script

  1. 01

    Inventory

    The SharePoint inventories of every project are downloaded and merged, then the PVsyst files are located.

  2. 02

    Download

    Only missing or updated PDFs are fetched, with automatic retries on HTTP 429 and a status report.

  3. 03

    Losses

    The loss diagram is read from PVsyst 6 to 8, in French and English, bifacial modules included.

  4. 04

    Orientations

    Each array yields its tilt, azimuth and modules, summed per pair and checked against the declared total.

  5. 05

    Merge

    Losses and orientations are combined into a single workbook, formatting included.

  6. 06

    Latest version

    Up to five PVsyst files per project: only the most recent is kept, and duplicates are flagged.

  7. 07

    Atlas

    Cross-referencing with the Atlas database cleans and enriches the retained data.

  8. 08

    Comparison

    The digital twin is extracted from the SynaptiQ API (970 plants, 1,794 module groups, 4,383 inverters), then every active plant is matched to its PVsyst and every discrepancy is classified.

Matching rules

  • A project is found by its code, otherwise by its name (at least 95% similarity).
  • A tilt/azimuth pair must be identical, or within 1° of tilt and 10° of azimuth.
  • The number of pairs and the number of modules per pair must agree; layout drawings serve as a cross-check.
  • The five losses (wiring, soiling, LID, mismatch, module quality) are compared one by one.

Outcome

Over 230 PVsyst studies showing discrepancies with the monitoring configuration were identified and reported to the teams; more than a hundred were being redone when I left. Most discrepancies concerned orientation, with an azimuth declared in the wrong cardinal direction, or the number of modules assigned to each orientation: long-standing discrepancies, built up over the years in both references.

A plant whose extraction is flagged as faulty leaves the analysis instead of skewing the result: it is checked by hand.
